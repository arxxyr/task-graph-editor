# 流程图编辑与现有问题研究

研究日期：2026-09-08。基线：`dev` 分支的 `e46a58f`，应用版本 `0.8.2`，Bevy `0.19.1`。
研究分支：`feat/graph-editing-research`。范围同时覆盖现有显示、交互问题及从只读扩展到可编辑的方案。
本文前半部分记录基线代码的研究结果，后续修复进度见文末；研究及修复均未连接机器人或写入远端。
其中“尚无编辑模型”和“协议待确认”等描述属于研究时点；当前 B/C/D 实施依据与验收以
[实施文档](graph-editing-implementation.md) 和 [执行器协议](graph-executor-protocol.md) 为准。

## 结论

现有分层布局、子图下钻、选中高亮、context 无损合并及远端原子保存可以继续使用。
流程图本身尚无写入模型，不能仅在详情栏换上输入控件就开放编辑。
建议先修复异常图的布局崩溃、连线歧义和导航重置，再建立保留完整 JSON 的命令与撤销层，
按属性编辑、结构编辑、画布直接操作的顺序交付。

现有流程图测试全部通过，但并未覆盖本次发现的场景。
优先级表示建议的修复顺序；损坏输入、有效输入和未来功能缺口分别说明，避免混为同一种问题。

## 现有能力与边界

| 层次 | 已有实现 | 对编辑的限制 |
| --- | --- | --- |
| 数据投影 | `TaskNode` 保存 `id/type/inputs/checkpoint/children`，`GraphEdge` 只有 `from/to` | 节点和边的其他字段只存在于 `raw_json`，不能由投影重建完整文件 |
| 保存 | `serialize_task_graph` 克隆原始 JSON，合并元数据与 context | 完全不读 `data.graph`，单独修改该字段不会写回 |
| 布局 | DFS 标记回边、最长路径分层、正交线段和外侧通道 | 位置由布局生成，没有手动位置状态，边也没有可供交互寻址的独立身份 |
| 交互 | 单击选中、再次按下已选复合节点进入子图、面包屑返回、详情查看 | 缺少节点/边增删改、画布拖动、独立缩放、多选、撤销与重做 |
| 界面更新 | 选中只更新颜色和详情；导航变化重建画布；BSN 插槽防止重复生成 | 文档加载与 context 结构变化共用版本，编辑流程时不能沿用这一粒度 |
| 远端保存 | 文档来源快照、输入刷新、同目录原子提交 | 尚无图校验、文档未保存状态、保存修订确认及远端内容冲突检查 |

## 已确认的问题

### 1. 高优先级：重复或保留 ID 缺少校验，布局可能崩溃

最小复现文件：

```json
{
  "map_id": "research",
  "task_id": "research",
  "config": {
    "context": {},
    "nodes": [{"id": "a"}, {"id": "a"}, {"id": "b"}],
    "edges": [{"from": "a", "to": "b"}]
  }
}
```

`model.rs:441–484` 接受重复 ID。`graph_layout.rs:142–156` 把两个零入度的 `a` 都加入队列，
重复处理后，`b` 的入度从 0 再减 1。使用当前实际模型和布局代码的隔离测试在 debug 构建中
复现 `attempt to subtract with overflow`。默认 release 关闭该溢出检查，不能宣称所有构建都会崩溃。
`rebuild_graph` 也没有可见视图守卫，因此加载文件时即使仍在参数视图，也会计算流程布局。

没有出边时，重复 ID 仍导致叠卡：`graph_layout.rs:204–225` 的坐标表以后项覆盖前项；
`model.rs:170–171` 的节点查找取第一项，所以两个不同类型的同名节点会显示第一项的内容。
真实节点若使用 `_entry` 或 `_exit`，还会与 `graph_layout.rs:174–176` 自动加入的虚拟节点冲突。

这是异常输入处理缺陷，尚无真实机器人文件命中的证据。修复应先产生带 JSON 路径的诊断，
阻止有歧义的子图进入布局；布局入口也要有可恢复的失败结果。
不能仅改成饱和减法，也不能静默去重，否则仍然隐藏原始节点和依赖。

验收：重复、空白及保留 ID 都有明确定位；错误图不 panic；原始 JSON 被完整保留；
诊断不得把不同层的同名节点误报为同层冲突。

### 2. 中优先级：有效图中的两条依赖完全共用水平线段

节点按 `a, b, c, d` 排列，边为：

```text
_entry → a       _entry → b
a → d           b → c
c → _exit       d → _exit
```

实际布局输出为：

```text
a → d: (147,192) → (147,216) → (405,216) → (405,240)
b → c: (405,192) → (405,216) → (147,216) → (147,240)
```

两条边在 `y=216, x=147…405` 完全重叠，方向相反。
`graph_layout.rs:308–321` 对所有顺行横移使用同一个层间中线；`243–246` 只检查是否遮住节点，
不检查边之间的重叠。`graph_view.rs:463–513` 将它们绘为同色线段，缺少独立选中和追踪手段，
用户难以从画面确定哪条依赖连接哪两个节点。

修复方向：层间横向轨道也分配通道，保留边的独立身份，增加悬停或选中时的完整路径高亮。
无需强求任意图完全无交叉，但不同依赖不能无标识地合并成一条线。
现有最长路径分层和非端点避障应保留。

验收：上述六条边可分别追踪；新增平行边、自环和回边样例；继续通过现有正交、避障和画布边界测试。

### 3. 中优先级：创建 context 位姿会清空流程图导航

复现步骤：打开包含复合节点和 null context 字段的文档 → 下钻子图 → 切回参数视图 →
将 null 创建为位姿 → 返回流程图。此时原下钻路径和选中状态均已丢失。

`worker_bridge.rs:521–538` 创建位姿后推进 `Editor::structure_version`，
而 `graph_view.rs:670–680` 把任何该版本变化都视作文件重载，调用 `nav.reset()`。
隔离 ECS 测试确认了这条版本传播路径；没有依赖鼠标时序。

修复方向：分开文档加载代次、context 结构版本和图结构版本。
每次重新加载文档（含同一路径重载）或清空文档时才无条件回根；图内修改应保留仍然有效的路径、选中目标和视口。
不要直接改变现有 `structure_version` 的含义，它同时参与数值校验和 ROS2 过期响应防护。

验收：context 创建位姿不影响流程导航；换文件仍回根；删除当前所在子图时退到最近有效祖先；
旧文档的 ROS2 响应仍被拒绝。

### 4. 中优先级：坏结构和缺失端点被静默省略

| 输入 | 当前行为 |
| --- | --- |
| 节点没有字符串 `id` | `filter_map` 丢弃节点，不显示原因 |
| 边端点不是字符串 | `filter_map` 丢弃边，不显示原因 |
| `{"id":"group","nodes":null}` | 被解释为存在空子图，仍可下钻 |
| 边指向不存在的 `ghost` | 模型保留边、工具栏计数包含它，布局不绘制 |

来源为 `model.rs:441–484`、`graph_layout.rs:179–184` 与 `graph_view.rs:196–202`。
错误子图和悬空边已用实际代码隔离复现。宽松读取有助于兼容文件，但必须告知画面不完整。

修复方向：导入结果携带结构诊断，显示原始/可绘制条数及错误路径；区分合法空子图和字段类型错误。
未知节点类型保留原始对象并标注未知，不能因为本工具不认识就删除。

验收：以上四类输入都有解释，损坏内容不因浏览或修改其他 context 而消失；
流程结构编辑只对已通过对应结构校验的范围开放。

### 5. 较低优先级：详情无法查看完整长参数

`graph_view.rs:548–561` 在生成参数文本时调用 `clip(&raw, 300)`，
超过 300 个字符的内容被替换为前 299 个字符加省略号。
数据仍完整保存在模型中，但滚动面板也无法找回未生成的后半段，当前没有全文展开或复制入口。
非对象 `inputs` 则统一显示“该节点没有输入参数”；是否允许这种形状，需以执行器协议为准。

修复方向：提供全文展开/复制和原始 JSON 查看；结构不符合预期时报告实际形状。
属性编辑控件必须使用原值初始化，不能将展示摘要作为编辑值。

## 从只读到可编辑的实现方案

### 数据、身份与无损保存

1. 保留加载时的 `raw_json`，继续作为 context 合并基线；新增图工作副本，保留完整的
   `config.nodes/edges` 及复合节点内联子图。只在图确实修改时将其合并进最终保存结果。
   `SubGraph` 作为只读派生视图，避免 JSON 与强类型模型都能独立修改。
2. 引入内部稳定的 `GraphKey/NodeKey/EdgeKey`，与文件里的业务 ID 分开。
   节点改名、数组插入、删除与撤销不能改变其他对象的身份；边不能用 `(from,to)` 作为唯一身份。
   内部 key 无需写入机器人文件，重新加载可重新建立映射。
3. 每条编辑命令包含文档身份、预期修订和明确目标。支持修改属性、重命名、增删节点/边及复合节点。
   校验成功后原子应用并记录逆操作；失败不改变文档、修订或撤销历史。
4. 删除节点及关联边是一笔事务，删除复合节点保留完整子树以供撤销；保留数组顺序、未知属性和缺省字段。
   修改单个输入只替换目标 JSON 值，不从 `TaskNode` 重造整个对象。
5. 重命名只更新已确认的同层显式边引用。表达式中可能引用业务 ID，必须先识别语法；
   不允许对所有字符串做全局替换。不识别的引用应报告并限制相关变更。
6. 未编辑字符串保持原字符串，整数与浮点类型沿用现有精度约束。
   外层 JSON 已经由 serde 重新格式化，“无损”指未编辑 JSON 值及内嵌字符串保留，不承诺文件逐字相同。

### 界面与历史状态

| 状态 | 变化时的处理 |
| --- | --- |
| 文档加载代次 | 清理旧历史、过期动作、选中和导航 |
| context 结构版本 | 仅重建参数树，继续用于既有数值校验与 ROS2 目标保护 |
| 图拓扑版本 | 更新相关子图的布局和连线，保留仍有效的视口和选择 |
| 图属性修订 | 更新标签或输入值，保持正在编辑控件的焦点和光标 |
| 选中及导航 | 选中只改样式/详情，切层才更换当前画布 |
| 画布视口与拖动预览 | 与机器人执行语义分离；拖动预览不生成大量历史记录 |
| 已保存内容状态 | 判断是否有未保存修改；撤销回保存状态时清除标记 |

属性表单沿用 `UiSet::Input → InputFlush → Update → Rebuild`，处理完本帧输入再执行编辑或保存。
BSN 重建继续走 `replace_slot_children` 和 `SlotPending`。跨帧生成的节点、边、详情输入带上文档身份，
避免旧实体事件误改新文档。

现有“再次按下已选复合节点即下钻”与拖动已选节点冲突，需要改成明确下钻按钮或真正的双击释放判定，
并加入拖动阈值和取消逻辑。节点增删先可通过工具栏和属性栏完整完成，直接拖拽连线后续接入同一命令层。

画布缩放需要独立于全局 `UiScale`，统一处理窗口物理像素、UI 逻辑像素、滚动偏移与图坐标。
手工位置可以保存在本地视图偏好中；没有协议依据前，不向机器人 JSON 添加 `x/y` 等编辑器字段。
图编辑历史应定义与 context 修改的关系：第一阶段可明确限定为“撤销流程修改”，
文档未保存状态仍须覆盖流程、context 和 `map_id/task_id` 元数据；如果做全局撤销，
context 输入、ROS2 回填及元数据修改也必须进入相同事务体系。`task_id` 还会影响远端文件改名，
需要同时保留已确认的实际文件名与当前编辑值，不能由撤销直接推断远端文件名。

### 校验与远端提交

复用当前文档来源绑定和原子保存协议，在生成 `WorkerRequest::SaveFile` 前补上图结构校验。
校验至少覆盖同层 ID 唯一、保留 ID、端点存在、内联子图形状及可编辑属性类型。
已有布局支持回边和自环，不能用“一律要求 DAG”替代机器人执行规则。

保存请求记录提交内容的修订/状态，回执只确认这份内容，不能把保存期间产生的新修改标成已保存。
保存失败保留历史和未保存状态。单调修订号用于拒绝过期动作，是否回到保存内容不能仅比较修订号大小。

原子替换保证文件不会半写入，并不检测其他程序在加载后是否改过文件。
若加入冲突保护，应在原子提交协议中校验基线内容，不能只在 UI 保存前提前读取一次来规避并发覆盖。

## 性能观察及协议待确认项

`canvas` 每次切层生成本层全部节点与边片段，没有视口裁剪。
`current.node(id)` 为线性查找，每个卡片调用一次，构建卡片部分具有二次扫描。
边对节点的避障检查也是逐一扫描；外侧通道的 `while + lanes.iter().any` 在密集图上还会反复扫描。
这些是代码级风险；未测真实用户任务规模和渲染帧耗时，不能据此宣称正常任务已经卡顿。

独立纯布局探针在合成的 80 节点、3241 条边的密集回边图中观察到约 0.63 秒计算和 21174 逻辑像素画布宽。
该探针以 `rustc -O` 编译原布局文件，使用最小数据类型适配，不含 Bevy ECS、文字布局和渲染，
仅用于说明极端图的退化风险，不是正式应用性能基线。后续应用代表性任务分别测布局时间、实体数和交互延迟，
再决定节点索引、通道索引、布局缓存或视口裁剪的优先级。

本仓库没有完整机器人节点注册表、输入/输出 schema、表达式语法或代表性的非空生产流程图夹具。
实施新增节点和结构编辑之前还需核对：

- 各节点类型的必填输入、默认值、输出与 checkpoint 语义。
- `sequence/parallel/condition/loop` 的实际执行规则、端口及分支编码方式。
- 业务 ID 引用范围、同端点多条边、入口/出口方向及孤立节点是否合法。
- 图布局坐标是否已有外部约定；代表性图规模及目标平台交互要求。

这些问题不影响本次研究结论，但在取得执行器依据前，只能验证 JSON 与结构一致性，不能宣称修改后的机器人流程可运行。

## 基础修复落实

用户确认先解决基础问题后，本分支按阶段 A 实施：
